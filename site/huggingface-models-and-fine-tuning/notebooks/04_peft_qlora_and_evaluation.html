Driving question¶

How can we attribute an improvement to an adapter and package it so another person can reproduce the comparison?

Keep this question in mind as you work. Each calculation, figure, and code cell gives you one more piece of the answer.

Before you begin¶

Recall base versus adapted models, fixed decoding, held-out prompts, adapter configuration, and the difference between validation loss and open-ended behavior.

Evaluation begins before training by freezing prompts, reference expectations, decoding settings, and rubric definitions. A useful comparison includes the unadapted base, a prompted baseline, LoRA, and QLoRA when available. It evaluates target behavior and retention, because an adapter can improve formatting while damaging unrelated capabilities. Per-example records make aggregate scores auditable.

Fine-tuning methods trade memory for flexibility¶

Full tuning, LoRA, and QLoRA store and update different sets of tensors.

Check your understanding: Which comparison is about engineering cost rather than an automatic ranking of output quality?

Learn and test: Compare adapter parameter counts¶

LoRA replaces a weight update with $\Delta W=BA$ of rank $r$. QLoRA quantizes frozen base weights while retaining higher-precision adapter training. Evaluation must compare the same prompts and decoding settings against the unadapted base.

Choosing an adaptation method¶

Full fine-tuning updates every parameter and optimizer state, offering maximum flexibility at high memory and storage cost. LoRA trains small low-rank matrices alongside frozen full-precision weights. QLoRA stores the frozen base in low precision while training adapters at higher precision, reducing memory further. These are engineering choices, not a guaranteed quality ordering.

Work the smallest useful example¶

A paired record stores prompt ID, model and adapter revisions, exact generation settings, outputs from each variant, latency, memory, and rubric fields. Holding prompts and decoding fixed removes two major confounders. Adapter storage may be small, but deployment also needs the compatible base, tokenizer, chat template, and software environment. Merging adds the adapter delta to base weights; it does not erase provenance or licensing obligations.

Learn and test: Define method contracts¶

For a dense d × k matrix, a LoRA update with rank r contains r(d+k) trainable values instead of dk. Rank should be treated as a capacity hyperparameter. Targeting more modules or using a larger rank increases expressiveness and adapter size. Merging adds the learned update into a compatible base model for simpler inference, but preserving the separate adapter is often better for provenance and reuse.

import torch
from peft import PeftModel
from transformers import AutoModelForCausalLM, AutoTokenizer
from course_helpers import (
    CLASSROOM_MODEL, CLASSROOM_REVISION,
    fixed_generate, directory_size,
)

adapter_dir = COURSE_ROOT / "adapters" / "classroom_smol_lora"
if not adapter_dir.exists():
    raise FileNotFoundError(
        "The PEFT adapter is missing. Run Lecture 03's two-step training cell first."
    )

tokenizer = AutoTokenizer.from_pretrained(adapter_dir)
dtype = torch.bfloat16 if torch.cuda.is_available() else torch.float32
base = AutoModelForCausalLM.from_pretrained(
    CLASSROOM_MODEL, revision=CLASSROOM_REVISION, dtype=dtype,
)
adapted = PeftModel.from_pretrained(base, adapter_dir, is_trainable=False).eval()
print("adapter size (MiB):", round(directory_size(adapter_dir) / 2**20, 2))

The directory must contain a PEFT configuration and adapter weights, and its base model must match the pinned revision. Loading succeeds before we attempt a merge; this separates an artifact-lineage failure from a numerical-equivalence failure.

Try it: generate base and adapter records¶

Before running: expect the run to be slow on CPU because each prompt is evaluated twice. Do not change the prompt subset after seeing weak examples.

records = []
for row in fixed_rows:
    prompt_messages = row["messages"][:-1]
    with adapted.disable_adapter():
        base_output = fixed_generate(
            adapted, tokenizer, prompt_messages, max_new_tokens=80
        )
    adapter_output = fixed_generate(
        adapted, tokenizer, prompt_messages, max_new_tokens=80
    )
    records.append({
        "prompt_id": row["id"],
        "prompt": prompt_messages,
        "reference": row["messages"][-1]["content"],
        "base_output": base_output,
        "adapter_output": adapter_output,
    })
print(json.dumps(records[0], indent=2, ensure_ascii=False)[:1800])

Each record now contains traceable text rather than an ellipsis or a manually typed claim. Inspect whether the output is nonempty and follows the requested form, then review factual support against the human response. With only two training steps, “no clear improvement” is a legitimate result.

Learn and test: Describe save, reload, and merge verification¶

Common misconception: merging an adapter does not remove its data or licensing provenance. The resulting weights still arise from both base and adaptation sources.

An adapter depends on a complete lineage¶

The base revision, tokenizer, training data, configuration, software, and evaluation all remain part of the artifact.

Try it: merge and verify logits¶

Merging folds the low-rank update into ordinary model weights. We compare one forward pass before and after merging. Small floating-point differences are expected; a changed tensor shape or large error indicates a packaging problem.

Inputs and outputs: The named Python objects enter this step; the printed values, token counts, tensor shapes, or saved files are the observations to check.

check_messages = fixed_rows[0]["messages"][:-1]
batch = tokenizer.apply_chat_template(
    check_messages, tokenize=True, add_generation_prompt=True,
    return_tensors="pt", return_dict=True,
)
device = next(adapted.parameters()).device
batch = {key: value.to(device) for key, value in batch.items()}
adapted.eval()
with torch.inference_mode():
    before = adapted(**batch).logits.float().cpu()
merged = adapted.merge_and_unload().eval()
merged_device = next(merged.parameters()).device
merged_batch = {key: value.to(merged_device) for key, value in batch.items()}
with torch.inference_mode():
    after = merged(**merged_batch).logits.float().cpu()
difference = (before - after).abs()
print("shape:", tuple(before.shape))
print("maximum absolute difference:", difference.max().item())
print("mean absolute difference:", difference.mean().item())

The shapes must match exactly and the maximum difference should be small relative to ordinary logits. Save the merged model only if deployment requires a single weight set; keeping the adapter separate is smaller and preserves the distinction between shared base weights and task-specific changes.

Packaging checklist¶

Save adapter weights/config, base model ID and revision, tokenizer/chat template, training config, data manifest hash, dependency versions, evaluation report, model card, and known limitations.

A realistic failure—and what it teaches us¶

Comparing different token budgets, selecting examples after seeing results, or reporting only showcase outputs invalidates attribution. A merged model should be checked against the unmerged base-plus-adapter using identical inputs and tolerance-aware logits. The model card must state intended use, data, limitations, and evaluation failures rather than functioning as promotional text.

Debugging habit: find the first expectation that failed—data identity, shape, normalization, causality, optimization, retrieval, grounding, or authorization. Then write the smallest check that separates that problem from the nearby possibilities.
